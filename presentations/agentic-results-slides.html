02

Experiment Procedure

The experiment uses a controlled retention workload so hint effects can be compared under the same distractor pressure.

Method Summary
  • Built a synthetic A → distractors → A replay retention workload.
  • Instrumented Dynamo and SGLang for direct worker attribution.
  • Swept distractor count upward to increase cache pressure.
  • Compared a no-hint control against a protected-hint run.
  • Injected hints from the frontend agent into the protected run.
  • Recorded first-request, replay, latency, and cache metrics at each step.
03

Direct Attribution Setup

This setup was instrumented so we can tie frontend hints to worker-side cache behavior, instead of relying only on loose time-window guesses.

Dynamo

Frontend + runtime instrumentation

Request path
Requests carry the synthetic probe ID, hint profile, and top-level priority fields into Dynamo runtime JSON logs.
Hint proof
We record whether the worker saw the hint object, whether top-level priority was present, and whether priority scheduling was enabled.
Glue scripts
The experiment wrappers automate model startup, sweep loops, report generation, and per-run artifact isolation.
SGLang

Worker + cache instrumentation

Transfer logging
We log host/device transfer direction, bytes moved, latency, and semantic request context from the patched worker.
Cache evidence
Replay rows record cached-token evidence and whether retention was still effective at that distractor count.
Priority path
Priority scheduling and radix eviction policy are surfaced into reports so we can distinguish “hint delivered” from “hint could matter here.”
Interpretation rule

“Hint was sent” is not enough. For a trustworthy conclusion we want: the worker received the hint, the worker had the priority mechanism enabled, and the protected run stayed warm longer than the control under the same pressure.

Control Run (No special protection)

The control row sends A without a protective priority hint. Its replay behavior tells us what ordinary retention looks like under the chosen policy.

Protected Run (Same prompt with high priority hint attached)

The protected row sends the same A request with a stronger priority profile. If the runtime respects it, replay A should remain warm deeper into the distractor sweep.

07

What This Report Shows

This slide condenses the run into an executive summary: what happened, why we trust it, and what the next experiment should probe.

Key Findings

Observed behavior in this run

  • The protected row stayed reusable deeper into the sweep than the control row.
  • Replay latency and replay cached-token evidence told the same story.
  • Worker-side priority readiness was enabled, so the hints could plausibly matter here.
Research Purpose

Why this matters

This setup lets us ask a sharper systems question: when we change frontend hints, do we actually change downstream cache behavior and replay cost, or are the hints only decorative metadata?

Interpretation

What we can safely claim

In this run, the protected hint profile was associated with longer replay survival under pressure than the no-hint control.

Caveat

What still needs care

Hint delivery alone is not proof of effect. We still want future runs to confirm the same separation across models, cache tiers, and tighter pressure schedules.

Next Step

Where this goes next

Repeat the same story across more models, more cache tiers, and different pressure levels to map the retention boundary of each hardware/runtime configuration.
